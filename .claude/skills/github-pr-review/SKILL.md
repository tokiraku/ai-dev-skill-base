# GitHub PRレビュースキル

## 概要

GitHubのPRを対象に、差分・CI結果・レビュー履歴を統合して評価し、**優先度別**にフィードバックを出力する。
通常のコードレビュー観点（品質・セキュリティ・設計）に加え、PR固有のリスク（回帰、CI失敗、変更範囲過大、説明不足）を重視する。

3つの観点（セキュリティ/信頼性・回帰/設計・テスト/CI/運用）それぞれで、**肯定的レビュアー（Advocate）と否定的レビュアー（Critic）を討論させて結論を出す**。単独エージェントの一発判定より、指摘の妥当性・重大度を突き合わせることで誤検知や過剰指摘を減らす。

ただし、この6エージェント討論はPRが大規模な場合のみフルで実行する。PR規模（変更ファイル数・行数）に応じて、小規模は単一エージェントの1パス分析、中規模は観点ごとに1エージェント（討論なし）に自動的に簡略化する（詳細は Step 2-0）。

## 実行手順

### Step 0: フォローアップ再確認モードの判定

Step 1でPRコンテキストを取得したら最初に、[perspective-checklist.md の「フォローアップ再確認モード」](./references/perspective-checklist.md#フォローアップ再確認モードstep-0)のトリガー条件に該当するか判定する。

- 該当する場合: Step 2以降のフルレビューではなく、同セクションの「実行内容」に従って前回指摘の対応確認を行う。新規論点のうち討論が必要なものだけ、該当観点のAdvocate/Critic 2エージェントを立てる。結果はStep 3・Step 4に合流させる。
- 該当しない場合: 通常どおりStep 2（PR規模判定以降）を実行する。

### Step 1: PRコンテキストの取得（MCP優先）

**まず GitHub MCP サーバーの有効化を試みる。** `mcp_github_*` ツールが見当たらない場合は、Claude Code の MCP 設定（`/mcp` コマンドまたは設定ファイル）で GitHub MCP サーバーが有効になっているか確認し、有効化するようユーザーに案内する。

GitHub MCPが利用可能な場合は、**必ずMCP経由**でPR情報を取得する。

1. `mcp_github_pull_request_read` の `get` でPRメタ情報を取得
2. `mcp_github_pull_request_read` の `get_files` / `get_diff` で変更ファイルと差分を取得
3. `mcp_github_pull_request_read` の `get_check_runs` / `get_status` でCI・チェック結果を取得
4. 必要に応じて `get_reviews` / `get_review_comments` / `get_comments` で既存指摘を確認

MCPが利用できない場合は、ローカル差分や共有されたPR情報を使ってレビューし、**MCP未使用である前提**を明示する。

取得した差分本文・CI結果・既存レビューコメントはテキストとして保持しておく。Step 2 で起動するサブエージェントは会話履歴を参照できないため、各エージェントのプロンプトに直接埋め込んで渡す必要がある。

#### 1-1. 事前ファクトチェック（メインスレッドで1回のみ）

差分中に、**客観的に検証可能な事実**（新規/更新された依存パッケージの正当性、CIの合否、参照しているURL・バージョンの実在性など）があれば、メインスレッドが**1回だけ**確認する（PyPI/npm確認、CI結果参照など）。確認できた事実は「既知の事実」として短くまとめ、Step 2で起動する全エージェントのプロンプトに埋め込む。

これにより、同一の検証（例: 追加ライブラリの正当性確認）を複数エージェントが独立に再実行することを防ぐ。エージェント側は討論ラウンド中もこの「既知の事実」を引用してよいが、自分で再検証する必要はない（後述のツール使用制限も参照）。

### Step 2: 観点別レビュー（3観点 × 肯定派/否定派レビュアーの討論、PR規模に応じて簡略化）

各観点につき「肯定的レビュアー（Advocate）」と「否定的レビュアー（Critic）」の2エージェントを立て、**独立分析 → 相互討論 → 収束**の手順で観点ごとの結論を出す（3観点 × 2エージェント = 計6エージェント）。
チェック項目・討論スタンスの詳細は [perspective-checklist.md](./references/perspective-checklist.md) を参照し、対応するセクションを各エージェントのプロンプトに含める。

#### 2-0. PR規模判定

変更ファイル数・変更行数から、[perspective-checklist.md の「PR規模による段階制」](./references/perspective-checklist.md#pr規模による段階制)に従って小規模/中規模/大規模を判定し、以降の実行内容を決める。段階制はオプトインではなく必ず判定する。

- **小規模**（1〜2ファイルかつ20行以内）: Step 2全体を省略し、単一エージェントの1パス分析のみ行う。以降の2-1〜2-3はスキップし、Step 3へ進む。
- **中規模**（3〜10ファイル、または21〜500行）: 下記2-1を「観点ごとに1エージェントのみ」に縮小し、討論（2-2）を省略する。各エージェントの指摘はそのままStep 3へ渡す。
- **大規模**（11ファイル以上、または500行超）: 下記2-1〜2-3をフルで実行する。

#### 2-1. 初期分析

**大規模**の場合、`subagent_type: general-purpose` で以下6エージェントを**単一メッセージで並列起動**する。各エージェントには Step 1 で取得した差分本文・CI結果・既存コメント・1-1で埋め込んだ「既知の事実」のうち該当する部分を渡し、「ファイルは読むだけで編集しないこと」を明示する。加えて、[perspective-checklist.md の「エージェントの探索ツール上限（全モード共通）」](./references/perspective-checklist.md#エージェントの探索ツール上限全モード共通)を全エージェントのプロンプトに必ず含める（小規模・中規模のエージェントも同様）。

| 観点 | Advocate（肯定的レビュアー） | Critic（否定的レビュアー） |
|---|---|---|
| セキュリティ・信頼性 | シークレット混入・入力検証・認可・例外処理・データ整合性を、実装意図を汲みつつレビュー | 同項目を、リスクを厳格に見積もってレビュー |
| 回帰・設計 | 機能回帰・境界条件・後方互換性・変更粒度・複雑度・命名/可読性・レイヤー構成を、文脈を汲みつつレビュー | 同項目を、厳格にレビュー |
| テスト・CI・運用 | CI結果・テスト充足度・PR説明の妥当性・PRサイズ・未解決指摘を、実務上の許容度を考慮してレビュー | 同項目を、厳格にレビュー |

両者とも同一のチェックリスト・優先度基準（🔴/🟡/🔵）を使い、`PR-xxx` 形式・ファイル:行番号付きで初期指摘リストを独立に作成する（相手の存在は伝えない）。スタンスの定義は [perspective-checklist.md](./references/perspective-checklist.md) の「討論スタンス」を厳守させる — Advocateも事実に基づかない擁護は禁止、Criticも存在しない問題の捏造は禁止。

**中規模**の場合、観点ごとに1エージェント（計3エージェント）を並列起動する。Advocate/Critic分割はせず、perspective-checklist.mdの「PR規模による段階制」で定義した中立スタンスでチェックリストを適用させる。

#### 2-1.5. 重複統合（大規模のみ）

3観点6エージェントの初期指摘リストが出揃った時点で、討論に入る**前**にメインスレッドが以下を行う。

1. 全観点の初期指摘リストをファイル:行番号で突き合わせ、同一箇所を指す指摘（観点をまたいで発見されたものも含む）をグルーピングする
2. グループ化できた指摘は、関連する観点のAdvocate/Criticすべてに「他観点でも同様の指摘がある」ことを伝えた上で、討論を1本化する（同じ論点について観点ごとに別々の討論ラウンドを回さない）
3. どの観点が主担当として討論ログをまとめるかを決める（通常は最も専門性の近い観点、例: シークレット混入ならセキュリティ観点）

#### 2-2. 討論（大規模のみ、最大3ラウンド）

観点ごとに、Advocate と Critic の初期指摘リストを互いに提示し、SendMessage で各エージェントを継続して反論・譲歩を行わせる。応答形式は [perspective-checklist.md](./references/perspective-checklist.md) の「討論時の応答形式」に従う。

0. **討論省略の判定**: 各指摘について、まず[perspective-checklist.md の「討論を省略して自動確定する条件」](./references/perspective-checklist.md#討論を省略して自動確定する条件)に該当するか確認する。該当する指摘は討論ラウンドを回さずメインスレッドが自動確定し、残った指摘のみ以降のラウンドにかける。
1. **ラウンド1**: 相手の初期指摘リストを提示し、指摘ごとに「同意（優先度そのまま採用）」「同意（優先度修正して採用）」「反対（却下、理由必須）」のいずれかで応答させる。ツール使用は[perspective-checklist.md の「討論ラウンド中のツール使用制限」](./references/perspective-checklist.md#討論ラウンド中のツール使用制限)に従う。
2. **ラウンド2〜3**: 前ラウンドで「反対」が残った指摘のみ、相手の反論を再提示し再応答させる。
3. **収束判定**: あるラウンドで、前ラウンドから双方の判定（同意/反対）が1件も変化しなければ、その時点で討論を打ち切り「合意」または「不一致確定」とする。
4. **上限到達**: ラウンド3を終えても不一致が残る指摘は「意見相違」として確定し、両者の見解をそのまま両論併記で保持する（どちらか一方を機械的に採用しない）。

#### 2-3. 観点内の結論確定（大規模のみ）

討論ログ（2-2の討論ラウンド、および2-2の0.で自動確定した指摘）をもとに、観点ごとに指摘を以下のいずれかに分類する。

| 分類 | 扱い |
|---|---|
| 討論省略で自動確定 | 確定した優先度でそのまま採用 |
| 合意成立（Advocateが同意） | Criticの指摘を、討論で合意した優先度で採用 |
| Criticが反対を撤回 | 指摘を却下（採用しない） |
| 3ラウンド経過も不一致 | 「意見相違」として、Advocate/Criticそれぞれの見解と理由を保持したまま次のステップへ渡す |

中規模の場合は2-1の3エージェントの指摘をそのままStep 3へ渡す（討論・自動確定の分類は行わない）。小規模の場合は2-0で行った単一エージェントの指摘をそのままStep 3へ渡す。

### Step 3: 結果統合・優先度分類

小規模は単一エージェントの指摘、中規模は3エージェントの指摘、大規模は3観点の結論確定済みリスト（Step 2-3の出力）を集約する。同一箇所への重複指摘は1件にまとめ、優先度が異なる場合は高い方を採用する。「意見相違」の指摘は統合後も両論併記のまま保持し、他の指摘と同様にファイル:行番号で重複判定する。

各観点は指摘生成時点で下記の優先度基準を使用済みだが、統合時にも整合性を確認する：

| 優先度 | 基準 | 対応期限の目安 |
|--------|------|----------------|
| 🔴 **必須修正** | バグ、脆弱性、CI失敗、データ破損/本番障害リスク、仕様回帰 | マージ前に必ず対応 |
| 🟡 **推奨** | 保守性・可読性低下、将来バグ化しやすい実装、テスト不足 | 次の修正タイミングまでに対応 |
| 🔵 **提案** | リファクタリング案、パフォーマンス改善、PR分割案 | 余裕があれば対応 |

補助観点として、必要に応じて以下のチェックリストも参照する：

- [品質・可読性チェックリスト](../code-review/references/quality-checklist.md)
- [セキュリティ・設計チェックリスト](../code-review/references/security-design-checklist.md)

### Step 4: フィードバック出力

レビュー結果は**指摘事項を先に**示し、最後に簡潔なサマリーを添える。
各指摘は、該当ファイル・行・差分文脈が追えるよう具体化する。
どの観点（セキュリティ/信頼性・回帰/設計・テスト/CI/運用）由来の指摘かはサマリーで内訳を示す。
討論で3ラウンド経過しても合意に至らなかった「意見相違」の指摘は、優先度セクションとは別に **⚖️ 意見相違（要ユーザー判断）** セクションを設け、Advocate/Critic双方の見解を併記する（一方を機械的に採用しない）。

### Step 5: コメント送信の確認と実行（ユーザー許可必須）

レビュー結果を提示した後、GitHubへコメント送信する必要がある場合は、**必ずユーザーに確認**する。

1. 送信候補コメント（要約・対象ファイル・行番号）をユーザーに提示
2. 送信可否を明示的に確認
3. **ユーザーが許可した場合のみ**、MCP経由でコメントを投稿

コメント投稿時は、状況に応じて以下を使用する：

- 単一コメント: `mcp_github_add_comment_to_pending_review`
- レビュー作成/送信: `mcp_github_pull_request_review_write`

許可が得られない場合は、コメント送信を行わず、下書き案のみ提示して終了する。

## 注意事項

- **GitHubへ投稿するコメントは必ず日本語で書く**（コード例・ファイルパス・技術用語は除く）
- PRレビューでは、概要説明よりも**具体的な指摘（Finding）を優先**する
- 可能な限り、差分上の実際の行に紐づけて指摘する
- 既存の指摘済み論点と重複する場合は、新規性の有無を明記する
- テスト不足を指摘する場合は、追加すべきテスト観点を具体化する
- ユーザーのメモリにあるプロジェクト規約（例: シークレット管理）を優先適用する
- GitHubへのコメント投稿は、**ユーザーの明示的な許可なしに実行しない**
- Step 0 のフォローアップ再確認モード判定は**必ず行う**。該当する場合は前回指摘の対応確認を優先し、通常のフルレビューへ安易に切り替えない
- Step 2-0 のPR規模判定は**必ず実行する**（オプトインではない）。大規模のみ6エージェント討論（3観点 × Advocate/Critic）をフル実行し、中規模は3エージェント（討論なし）、小規模は単一エージェントに簡略化する
- 討論は最大3ラウンドで打ち切る。3ラウンドを超えて延長しない — 収束しない指摘は「意見相違」として両論併記する（どちらか一方を機械的に優先しない）
- 討論に入る前に、[討論を省略して自動確定する条件](./references/perspective-checklist.md#討論を省略して自動確定する条件)に該当する指摘は討論ラウンドにかけない — 討論は🔴の要否や事実の真偽が割れている指摘に絞る
- すべてのエージェントのプロンプトに[エージェントの探索ツール上限（全モード共通）](./references/perspective-checklist.md#エージェントの探索ツール上限全モード共通)を含める。討論ラウンド中はさらに厳しい[討論ラウンド中のツール使用制限](./references/perspective-checklist.md#討論ラウンド中のツール使用制限)を適用し、Step 1-1で埋め込んだ「既知の事実」とラウンド1で得た事実の引用のみで応答させる
- 全エージェントは読み取り専用として動作させる。ファイル編集・コメント投稿は本体（メインスレッド）でのみ行う
- GitHubへ実際にコメント投稿する際は、「意見相違」の指摘は両論併記のまま送るか、ユーザーに個別に採否を確認してから送る
- レビューコメントへの実際の**修正実装**は本スキルの対象外。`github-pr-review-response` スキルに委ねる
