# タスク実装スキル

## 概要

`tasks/todo.md` のタスクリストをもとに開発を進める。
タスクの選択 → 要件確認 → 実装 → セルフレビュー → 進捗更新 の流れを一貫して実行する。

---

## 実行手順

### Step 1: タスクリストの読み込み

`tasks/todo.md` を Read で読み込む。
存在しない場合は「タスクリストが見つかりません。`/create-tasks` を先に実行してください」と出力して終了する。

---

### Step 2: 対象タスクの特定

#### 引数が渡された場合

- `next` が指定された場合: フェーズ順・優先度順（Must Have → Should Have）で最初の未完了タスクを自動選択する
- タスクID（例: `FR-001-01`）が指定された場合: そのタスクを対象にする
- タスクIDが見つからない場合はエラーを出して一覧を提示する

#### 引数が省略された場合

未完了タスクを以下の形式で一覧表示し、AskUserQuestion でどれを実装するか確認する。

```
## 未完了タスク一覧

### フェーズ1: 設計・準備
- [ ] [SETUP-001] プロジェクト初期設定（Must Have）

### フェーズ3: ドメイン層
- [ ] [FR-001-01] User エンティティを実装する（Must Have）
- [ ] [FR-001-02] Email 値オブジェクトを実装する（Must Have）

どのタスクを実装しますか？タスクIDを入力してください（例: FR-001-01）
または "next" で優先度順の最初のタスクを自動選択します。
```

---

### Step 3: タスク詳細と要件の確認

対象タスクの詳細を `tasks/todo.md` から抽出する：

- タスクID・タスク名
- 優先度
- 関連要件ID（FR-xxx / NFR-xxx など）
- 完了基準

関連要件IDがある場合は `docs/requirements/` 配下の該当ドキュメントを Read して受け入れ基準（Given/When/Then）を確認する。

技術スタック・アーキテクチャルールが不明な場合は `.claude/rules/` 配下のルールファイルを読む。

---

### Step 4: 実装計画の提示・承認

実装方針をユーザーに提示してから着手する。

```
## 実装計画: [タスクID] タスク名

### 対象タスク
- **タスクID**: タスクID
- **完了基準**: 〇〇が満たされていること
- **関連要件**: FR-001（ユーザー登録機能）

### 実装方針
1. 〇〇を作成する（ファイルパス）
2. 〇〇に〇〇を追加する（ファイルパス:行番号）
3. ユニットテストを作成する（ファイルパス）

### 影響範囲
- 新規ファイル: N個
- 変更ファイル: N個

この計画で実装を開始してよいですか？
```

ユーザーの承認を得てから Step 5 に進む。
修正があれば計画を更新して再提示する。

---

### Step 5: ブランチ作成

実装に着手する前に、`develop` ブランチから作業ブランチを作成する。

#### ブランチ名の規則

```
<type>/<task-id>-<short-description>
```

- `<type>`: タスクの種別に応じて以下から選ぶ
  - `feat` — 機能実装（FR-xxx 系タスク）
  - `fix` — バグ修正
  - `chore` — セットアップ・設定・ツール系（SETUP-xxx 系タスク）
  - `refactor` — リファクタリング
  - `test` — テストのみ
- `<task-id>`: タスクID を小文字に変換（例: `fr-001-01`）
- `<short-description>`: タスク名を短く英語にしたもの（ケバブケース）

例: `feat/fr-001-01-user-entity`

#### 実行手順

1. `develop` ブランチに切り替える
   ```bash
   git checkout develop
   ```
2. 最新の `develop` を取得する
   ```bash
   git pull origin develop
   ```
3. 作業ブランチを作成して切り替える
   ```bash
   git checkout -b <branch-name>
   ```

ブランチ作成後、ブランチ名をユーザーに報告してから Step 6 に進む。

---

### Step 6: 実装

承認された計画に従って実装する。

#### 実装時のルール

- **アーキテクチャルール準拠**: `.claude/rules/architecture.md` のDDDレイヤー構成に従う
- **コードスタイル準拠**: `.claude/rules/code-style.md` の命名規則・フォーマットに従う
- **セキュリティルール準拠**: `.claude/rules/security.md` の禁止事項を守る
- **1タスク = 1コミット単位**: タスクの粒度で完結する実装にする
- **テストを同時に書く**: ドメイン層はユニットテスト、インフラ層は統合テストを必須とする（`.claude/rules/testing.md` 参照）

#### 既存コードがある場合

- 変更対象ファイルを必ず Read してから Edit する
- 既存の命名規則・パターンに合わせる
- 既存テストが壊れないよう確認する

#### 実装中の報告

各ファイル作成・編集後に「✓ `ファイルパス` を作成/更新しました」と短く報告する。

---

### Step 7: セルフレビュー

実装完了後、以下の観点でセルフチェックを行う。

| チェック項目 | 確認内容 |
|------------|---------|
| **完了基準の充足** | `tasks/todo.md` の完了基準をすべて満たしているか |
| **受け入れ基準の充足** | Given/When/Then がすべて満たされているか |
| **アーキテクチャ準拠** | レイヤー間の依存方向が正しいか |
| **テスト網羅** | ハッピーパス・エラーパス・エッジケースが揃っているか |
| **セキュリティ** | 外部入力のバリデーション・シークレットのハードコードがないか |
| **未使用コード** | 未使用のインポート・変数がないか |

問題が見つかった場合はその場で修正する。

---

### Step 8: tasks/todo.md の進捗更新

セルフレビューが完了したら `tasks/todo.md` を更新する。

- 完了したタスクの `[ ]` を `[x]` に変更する
- 「進捗サマリー」テーブルの完了数をインクリメントする

```markdown
<!-- 変更前 -->
- [ ] [FR-001-01] User エンティティを実装する

<!-- 変更後 -->
- [x] [FR-001-01] User エンティティを実装する
```

---

### Step 9: 完了報告

```
## 実装完了: [タスクID] タスク名

### 実装内容
| ファイル | 操作 | 概要 |
|---------|------|------|
| `path/to/file.ts` | 新規作成 | User エンティティクラス |
| `path/to/file.test.ts` | 新規作成 | User エンティティのユニットテスト |

### 完了基準の確認
- [x] 〇〇が実装されている
- [x] ユニットテストが全件パス

### 作業ブランチ
- ブランチ: `<branch-name>`

### 次のアクション（推奨）
- コミット・プッシュ: `/github-commit-push`
- PRを作成する: `/github-create-pr`
- コードレビュー: `/code-review <実装ファイルパス>`
- 次のタスクに進む: `/implement-task next`
```

---

## 注意事項

- **実装は必ず専用の作業ブランチで行う** — `develop` や `main` に直接コミットしない
- **実装前に必ず計画を提示してユーザーの承認を得る** — 無断で実装を開始しない
- 要件ドキュメント・アーキテクチャルールが存在する場合は必ず参照してから実装する
- 完了基準が曖昧なタスクは着手前に AskUserQuestion で確認する
- テストが走る環境（`npm test` / `pytest` 等）がある場合はテストを実行して結果を確認する
- 実装が予想より大きくなる場合は、タスクをさらに分割してユーザーに確認する
- `tasks/todo.md` の更新は実装完了・確認済みの後に行う（途中状態で更新しない）
- セルフレビューで問題が見つかった場合は、ユーザーに報告してから修正する
