# テスト検証チェックリスト（3エージェント用）

`generate-tests` スキルの Step 5 で並列起動する3エージェントに、それぞれ該当セクションをプロンプトへ含める。

---

## 1. 網羅性レビューエージェント

**入力として渡すもの**: 仕様書ファイル、生成したテストファイル一覧

**チェック項目**:

- [ ] 仕様書内の全 FR-xxx / NFR-xxx にテストケースが対応しているか
- [ ] Must Have 要件のすべてがテスト化されているか（欠落は🔴）
- [ ] 各要件の Given/When/Then すべてがカバーされているか（一部シナリオの欠落は🟡）
- [ ] ハッピーパスだけでなくエラーパスもカバーされているか
- [ ] エッジケース（空・null・境界値・最大値・同時実行等、仕様書に記載があるもの）が抜けていないか
- [ ] 逆に、仕様書に存在しない振る舞いを勝手にテスト化していないか（過剰なテストは🔵で指摘）

**出力形式**: `code-review` と同じ優先度（🔴/🟡/🔵）でファイル:行番号付き。各指摘に対応する要件IDを明記する。

---

## 2. 品質レビューエージェント

**入力として渡すもの**: `.agents/rules/testing.md`、生成したテストファイル一覧

**チェック項目**:

- [ ] テスト名が「状況→操作→期待結果」形式になっているか
- [ ] AAA（Arrange/Act/Assert）構造で書かれているか
- [ ] 1テストにつき検証している振る舞いが1つに絞られているか（1アサーション原則）
- [ ] モックが外部境界（DB・外部API・時刻・乱数）以外に使われていないか（ドメインロジック内部のモックは🔴）
- [ ] テストデータがテストケース内で完結しているか（共有ファイル・共有状態への依存は🟡）
- [ ] テストの実行順序に依存していないか
- [ ] `sleep`/`wait` による時間依存テストがないか（🔴）
- [ ] テストピラミッド（domain=ユニット必須、infrastructure=統合必須、E2Eは最小限）に沿っているか
- [ ] 命名規則・フォーマット（`.agents/rules/code-style.md`: インデント・命名規則等）に準拠しているか

**出力形式**: `code-review` と同じ優先度（🔴/🟡/🔵）でファイル:行番号付き。

---

## 3. 正当性/妥当性レビューエージェント

**入力として渡すもの**: 実装対象コード（存在する場合）、生成したテストファイル一覧

**チェック項目（「実装が壊れていてもこのテストは通ってしまわないか」を軸に評価する）**:

- [ ] アサーションが実質的に何も検証していない（tautological）ものがないか（例: `expect(true).toBe(true)`、返り値の型だけ確認して値を見ていない等）— 🔴
- [ ] 期待値が仕様書の受け入れ基準と矛盾していないか（誤った期待値）— 🔴
- [ ] アサーションが弱すぎないか（存在確認・undefinedでないことの確認のみ等、本来検証すべき値を見ていない）— 🟡
- [ ] 実装の内部構造・プライベートな詳細に過度に依存していないか（リファクタリングだけで壊れるテストになっていないか）— 🟡
- [ ] エラーケースのテストで、例外の型・メッセージ等を正しく検証しているか（catchして何もしない等の握り潰しがないか）— 🔴
- [ ] モックの戻り値がテストの前提（Arrange）と矛盾していないか
- [ ] 境界値テストが実際に境界（例: N と N+1）を検証しているか、名前だけ境界値でずれた値になっていないか

**出力形式**: `code-review` と同じ優先度（🔴/🟡/🔵）でファイル:行番号付き。可能であれば「このテストを壊さずに実装をどう壊せるか」の具体例を添える。
