# PRレビュー観点別チェックリスト

`github-pr-review` スキルの Step 2 で起動するエージェントに、それぞれ該当セクションをプロンプトへ含める。PR規模（下記「PR規模による段階制」）に応じて、大規模は6エージェント（3観点 × Advocate/Critic）の討論形式、中規模は観点ごとに1エージェントの単独判定形式で使う。

各エージェントは以下の優先度基準で指摘を出す。

| 優先度 | 基準 | 対応期限の目安 |
|--------|------|----------------|
| 🔴 **必須修正** | バグ、脆弱性、CI失敗、データ破損/本番障害リスク、仕様回帰 | マージ前に必ず対応 |
| 🟡 **推奨** | 保守性・可読性低下、将来バグ化しやすい実装、テスト不足 | 次の修正タイミングまでに対応 |
| 🔵 **提案** | リファクタリング案、パフォーマンス改善、PR分割案 | 余裕があれば対応 |

---

## PR規模による段階制

`github-pr-review` スキルの Step 2 は、PRの規模に応じて3段階のいずれかで実行する。判定は**変更ファイル数を主基準、変更行数（追加+削除）を補助基準**とする。ファイル数と行数の基準が異なる規模を指す場合は**大きい方の規模**を採用する（例: 2ファイルだが600行変更 → 大規模）。

| 規模 | 判定基準 | 実行内容 |
|------|----------|----------|
| 小規模 | 変更ファイル数 1〜2 **かつ** 変更行数合計 20行以内 | Step 2を省略し、単一エージェントの1パス分析のみ（討論なし） |
| 中規模 | 変更ファイル数 3〜10、**または** 変更行数合計 21〜500行 | 観点ごとに1エージェントのみ起動する（Advocate/Critic分割・討論は行わない）。討論スタンスは使わず、下記チェックリストのみで指摘を出す |
| 大規模 | 変更ファイル数 11以上、**または** 変更行数合計 500行超 | 現行の6エージェント討論（3観点 × Advocate/Critic）をフルで実行する |

中規模の1エージェントは、Advocate/Criticのどちらにも偏らず「実装意図を汲みつつ、事実に基づくリスクは厳格に指摘する」中立スタンスでチェックリストを適用する。

## エージェントの探索ツール上限（全モード共通）

小規模/中規模/大規模いずれのエージェントにも、プロンプトへ以下を必須で含める。初期分析・討論ラウンドを問わず適用する共通の上限であり、討論ラウンドにはこれに加えて「討論ラウンド中のツール使用制限」がさらに重なる。

- 差分本文・チェックリスト・Step 1-1の「既知の事実」だけで判断できる指摘は、追加の探索（Read/Grep等）を行わない
- 判断がつかない項目についてのみ、最小限（目安5〜8回）のRead/Grepで確認する
- diffの再取得やテスト実行（`pytest` 等）は、既知の事実だけでは結論が出ない場合に限定する

## 討論スタンス（共通・全観点で使用）

各観点で立てる2エージェントには、以下のスタンスを厳守させる。**どちらも事実に基づく指摘のみを扱う** — スタンスは重大度の見積もり方・許容度の違いであり、捏造や事実誤認を正当化しない。

### 肯定的レビュアー（Advocate）

- 実装の意図・文脈（PR説明、既存コードの慣習）を汲み取り、指摘の重大性を過大評価しない
- 「動くが理想的ではない」程度のものを🔴に釣り上げない。妥当な範囲で優先度を下げる/却下する立場を取る
- ただし、実際に事実として問題がある（脆弱性がある、テストがない、CIが落ちている等）ものを「問題なし」と偽ることは禁止
- Criticの指摘に同意する場合は率直に同意する。スタンスを守るために無理に反論を作らない

### 否定的レビュアー（Critic）

- リスクを厳格に評価し、疑わしい箇所・確認が取れない箇所は指摘する
- 「たぶん大丈夫」を許容しない。境界条件・異常系・悪意ある入力を積極的に想定する
- ただし、コード上の根拠がない憶測だけで指摘を作らない（存在しない問題の捏造は禁止）
- Advocateの反論が妥当であれば率直に譲歩する。スタンスを守るために無理に指摘を維持しない

### 討論時の応答形式（共通）

相手の指摘リストを受け取ったら、指摘ごとに以下の形式で応答する。

```
[PR-xxx] <判定: 同意 / 優先度修正して同意 / 反対>
理由: <具体的根拠。コード上の事実に基づくこと。憶測や「念のため」は不可>
（判定が「優先度修正して同意」の場合）修正後優先度: 🔴/🟡/🔵
```

「反対」の場合、次ラウンドで相手からの再反論を受け取ったら、同じ形式で再応答する（同意に転じてもよいし、反対を維持してもよい）。前ラウンドと判定が変わらない場合はその旨を明記する（収束判定に使う）。

### 討論を省略して自動確定する条件

以下のいずれかに該当する指摘は、討論ラウンドに入れず**メインスレッドが自動確定**する（両エージェントの初期指摘リストを突き合わせた時点で判定できる）。

- Advocate・Criticの優先度判定が完全一致 → その優先度で採用
- 優先度差が隣接1段階のみ（🟡⇔🔵）→ 高い方の優先度で自動採用
- 一方のみが指摘し、もう一方が明確に反対していない（単に触れていないだけ）→ 指摘した側の優先度で採用

討論ラウンドを実施するのは、次のいずれかに該当する場合のみとする。

- 一方が指摘の**存在自体**（事実の真偽）を否定している
- 優先度差が2段階（🔴⇔🔵）
- 🔴の要否そのものが割れている（🔴と主張する側と、それを却下したい側がいる）

### 討論ラウンド中のツール使用制限

討論ラウンド（2-2）は「エージェントの探索ツール上限（全モード共通）」よりさらに厳しく、**ラウンド1で得た事実・Step 1で埋め込まれた「既知の事実」の引用のみ**を根拠として使う。Docker build・`pip install`・WebSearch等による新規の再検証は原則禁止する。相手が初めて提示した未検証の事実（新規ライブラリ名など）についてのみ、最小限の確認を1回だけ許可する。

## フォローアップ再確認モード（Step 0）

以下のいずれかに該当する場合、通常のPR規模判定（Step 2-0以降のフルレビュー）ではなく、この再確認フローを使う。

- ユーザーから「返信を受けて再確認して」「指摘の対応を確認して」等、フォローアップの再レビューを明示的に依頼された
- Step 1で取得した既存レビューコメントに対応完了を示すコメント（「対応しました」「Fixed」等）があり、かつ本スキルによる過去のレビュー結果が存在する（両方を満たす場合のみ。片方だけでは通常フローを使う）

### 実行内容

1. **前回指摘の検証（メインスレッド直接確認・討論なしが原則）**: 前回レビューで指摘した項目ごとに、該当ファイル・現在の差分をメインスレッドが直接確認し、「対応済み」「未対応」「一部対応」を判定する。エージェントは起動しない。
   - 変更ファイル数が多く見落としリスクが高い場合（目安: 3ファイル以上、中規模相当）のみ、観点ごとに1エージェント（討論なし・「PR規模による段階制」の中規模と同じ形式）を起動して検証を分担する。
2. **新規論点の扱い**: 検証中に新たに見つかった、前回指摘になかった論点は以下のいずれかで扱う。
   - 優先度判定に迷いがない場合: そのまま指摘としてStep 3へ渡す（討論なし）
   - 優先度が🔴か🔵かで大きく割れる場合（メインスレッド自身の判断が割れる、または検証エージェント間で評価が食い違う）のみ、該当する1観点についてAdvocate/Critic 2エージェントを立てて討論する（討論ルール・ラウンド数上限は通常フローの2-2と同じ）。他の観点・エージェントは起動しない。
3. **前回の意見相違の引き継ぎ**: 前回「意見相違」として保留した指摘は、今回の差分・コメントに新情報があればメインスレッドが該当箇所を確認し、解消していれば「解消」として除外する。未解消の場合は討論をやり直さず、前回の両論併記のまま維持する。

この再確認フローの結果もStep 3（結果統合）・Step 4（出力）に合流させる。出力には「前回指摘の対応状況」（対応済み/未対応/一部対応の件数）を追加する。

**`github-pr-review-response` との役割分担**: 本モードは前回指摘への**対応状況を確認する読み取り専用の再レビュー**。レビューコメントを受けて実際にコードを**修正**する場合は `github-pr-review-response` スキルを使う。

## 1. セキュリティ・信頼性（Advocate / Critic 共通チェックリスト）

Advocate・Critic双方にこのセクションを渡し、上記「討論スタンス」を適用させる。

**入力として渡すもの**: PR差分本文、変更ファイル一覧

**注意（Advocateへの制約）**: シークレット・APIキー混入が実際に確認できた場合、それは事実であり許容度の問題ではない。Advocateもこれを「問題なし」「意図的だから許容」と擁護してはならず、必ず🔴として同意すること。

**最優先チェック（シークレット・APIキー混入）**:

- [ ] APIキー・アクセストークン・シークレットキーの文字列リテラル（`sk-...`, `ghp_...`, `AKIA...` 等のプレフィックスパターン含む）
- [ ] パスワード・認証情報の直接記述（`password = "..."`, `secret = "..."` 等）
- [ ] 接続文字列に認証情報が含まれるもの（`postgresql://user:pass@host/db` 等）
- [ ] `.env` / `credentials.*` / `*.pem` / `*.key` 等のシークレットファイル自体の差分への混入
- [ ] `.gitignore` に `.env` 等のシークレットファイルが除外されているか

**通常チェック**:

- [ ] 入力検証がシステム境界（APIエンドポイント・ユーザー入力）で行われているか
- [ ] 認可チェックがサーバーサイドで行われているか（クライアント側のみの権限チェックは🔴）
- [ ] 例外処理でエラーを握りつぶしていないか（空catch）
- [ ] SQLインジェクション・XSS・コマンドインジェクション・パストラバーサル対策が適切か
- [ ] データ整合性（トランザクション境界、部分更新時の不整合）に問題がないか
- [ ] スタックトレース・内部パス等の情報漏洩がレスポンス/ログに含まれていないか

**出力形式**: `PR-xxx` 形式、優先度（🔴/🟡/🔵）、ファイル:行番号付き。シークレット混入を発見した場合は必ず🔴で最上位に報告する。

## 2. 回帰・設計（Advocate / Critic 共通チェックリスト）

Advocate・Critic双方にこのセクションを渡し、上記「討論スタンス」を適用させる。

**入力として渡すもの**: PR差分本文、変更ファイル一覧、既存レビューコメント（あれば）

**チェック項目**:

- [ ] 既存仕様を壊す変更がないか（呼び出し元・API契約への影響）
- [ ] 境界条件（空・null・最大値・並行実行）の考慮漏れがないか
- [ ] 後方互換性が必要な箇所で破壊的変更をしていないか
- [ ] 変更粒度が適切か（1PRに複数の無関係な変更が混在していないか）
- [ ] 複雑度が不必要に上昇していないか（ネスト過多、責務過多な関数）
- [ ] 命名・可読性が規約（`.agents/rules/code-style.md`）に沿っているか
- [ ] `.agents/rules/architecture.md` のレイヤー構成・依存方向（フロント/バック分離、DDDの内側方向依存）に違反していないか

**出力形式**: `PR-xxx` 形式、優先度（🔴/🟡/🔵）、ファイル:行番号付き。

## 3. テスト・CI・運用（Advocate / Critic 共通チェックリスト）

Advocate・Critic双方にこのセクションを渡し、上記「討論スタンス」を適用させる。

**入力として渡すもの**: CI/チェック結果、変更ファイル一覧、PRタイトル・説明文

**注意（Advocateへの制約）**: CIチェックの失敗は事実であり許容度の問題ではない。Advocateもこれを「軽微」と擁護してはならず、必ず🔴として同意すること。

**チェック項目**:

- [ ] CIチェックが失敗/未実行のまま残っていないか（失敗は🔴）
- [ ] 変更点に対応するテストが追加/更新されているか（`.agents/rules/testing.md` のテストピラミッド準拠）
- [ ] domain層相当の変更にユニットテストがあるか、infrastructure層相当の変更に統合テストがあるか
- [ ] エッジケース（空・null・境界値）のテストが漏れていないか
- [ ] PRタイトル・説明が変更内容を正確に反映しているか
- [ ] PRサイズが大きすぎてレビューしづらくないか（分割余地があれば🔵で提案）
- [ ] 既存の指摘済み論点（レビューコメント）が未解決のまま残っていないか

**出力形式**: `PR-xxx` 形式、優先度（🔴/🟡/🔵）、ファイル:行番号付き。CI失敗を発見した場合は失敗しているチェック名を明記する。
