# GitHub PRレビュースキル

## 概要

GitHubのPRを対象に、差分・CI結果・レビュー履歴を統合して評価し、**優先度別**にフィードバックを出力する。
通常のコードレビュー観点（品質・セキュリティ・設計）に加え、PR固有のリスク（回帰、CI失敗、変更範囲過大、説明不足）を重視する。

## 実行手順

### Step 1: PRコンテキストの取得（MCP優先）

**まず GitHub MCP サーバーの有効化を試みる。** `mcp_github_*` ツールが見当たらない場合は、Claude Code の MCP 設定（`/mcp` コマンドまたは設定ファイル）で GitHub MCP サーバーが有効になっているか確認し、有効化するようユーザーに案内する。

GitHub MCPが利用可能な場合は、**必ずMCP経由**でPR情報を取得する。

1. `mcp_github_pull_request_read` の `get` でPRメタ情報を取得
2. `mcp_github_pull_request_read` の `get_files` / `get_diff` で変更ファイルと差分を取得
3. `mcp_github_pull_request_read` の `get_check_runs` / `get_status` でCI・チェック結果を取得
4. 必要に応じて `get_reviews` / `get_review_comments` / `get_comments` で既存指摘を確認

MCPが利用できない場合は、ローカル差分や共有されたPR情報を使ってレビューし、**MCP未使用である前提**を明示する。

取得した差分本文・CI結果・既存レビューコメントはテキストとして保持しておく。Step 2 で起動するサブエージェントは会話履歴を参照できないため、各エージェントのプロンプトに直接埋め込んで渡す必要がある。

### Step 2: 観点別レビュー（3エージェント並列起動）

**3つの Agent を単一メッセージで並列起動**して、観点別にレビューする。
各エージェントは `subagent_type: general-purpose` とし、プロンプトで「ファイルは読むだけで編集しないこと」を明示する。
チェック項目の詳細は [perspective-checklist.md](./references/perspective-checklist.md) を参照し、対応するセクションを各エージェントのプロンプトに含める。

| エージェント | 観点 |
|---|---|
| セキュリティ・信頼性レビュー | シークレット・APIキー混入チェック（最優先）、入力検証、認可、例外処理、データ整合性 |
| 回帰・設計レビュー | 機能回帰リスク、境界条件漏れ、後方互換性、変更粒度、複雑度、命名・可読性、レイヤー構成違反 |
| テスト・CI・運用レビュー | CI失敗/未実行チェック、テスト不足、PRタイトル/説明の妥当性、レビューしづらい巨大PR、未解決の既存指摘 |

各エージェントには Step 1 で取得した差分本文・CI結果・既存コメントのうち該当する部分を渡し、[perspective-checklist.md](./references/perspective-checklist.md) の優先度基準（🔴/🟡/🔵）で `PR-xxx` 形式・ファイル:行番号付きの指摘を返させる。

変更が1ファイルかつ数行程度のごく小規模なPRの場合は、3エージェント並列起動を省略し単一パスでの分析に簡略化してよい。それ以外は必ず並列起動する（オプトインではない）。

### Step 3: 結果統合・優先度分類

3エージェントの指摘を集約する。同一箇所への重複指摘は1件にまとめ、優先度が異なる場合は高い方を採用する。

各エージェントは指摘生成時点で下記の優先度基準を使用済みだが、統合時にも整合性を確認する：

| 優先度 | 基準 | 対応期限の目安 |
|--------|------|----------------|
| 🔴 **必須修正** | バグ、脆弱性、CI失敗、データ破損/本番障害リスク、仕様回帰 | マージ前に必ず対応 |
| 🟡 **推奨** | 保守性・可読性低下、将来バグ化しやすい実装、テスト不足 | 次の修正タイミングまでに対応 |
| 🔵 **提案** | リファクタリング案、パフォーマンス改善、PR分割案 | 余裕があれば対応 |

補助観点として、必要に応じて以下のチェックリストも参照する：

- [品質・可読性チェックリスト](../code-review/references/quality-checklist.md)
- [セキュリティ・設計チェックリスト](../code-review/references/security-design-checklist.md)

### Step 4: フィードバック出力

レビュー結果は**指摘事項を先に**示し、最後に簡潔なサマリーを添える。
各指摘は、該当ファイル・行・差分文脈が追えるよう具体化する。
どのエージェント（観点）由来の指摘かはサマリーで内訳を示す。

### Step 5: コメント送信の確認と実行（ユーザー許可必須）

レビュー結果を提示した後、GitHubへコメント送信する必要がある場合は、**必ずユーザーに確認**する。

1. 送信候補コメント（要約・対象ファイル・行番号）をユーザーに提示
2. 送信可否を明示的に確認
3. **ユーザーが許可した場合のみ**、MCP経由でコメントを投稿

コメント投稿時は、状況に応じて以下を使用する：

- 単一コメント: `mcp_github_add_comment_to_pending_review`
- レビュー作成/送信: `mcp_github_pull_request_review_write`

許可が得られない場合は、コメント送信を行わず、下書き案のみ提示して終了する。

## 注意事項

- **GitHubへ投稿するコメントは必ず日本語で書く**（コード例・ファイルパス・技術用語は除く）
- PRレビューでは、概要説明よりも**具体的な指摘（Finding）を優先**する
- 可能な限り、差分上の実際の行に紐づけて指摘する
- 既存の指摘済み論点と重複する場合は、新規性の有無を明記する
- テスト不足を指摘する場合は、追加すべきテスト観点を具体化する
- ユーザーのメモリにあるプロジェクト規約（例: シークレット管理）を優先適用する
- GitHubへのコメント投稿は、**ユーザーの明示的な許可なしに実行しない**
- Step 2 の3エージェント並列レビューは、小規模PR（1ファイルかつ数行程度）を除き**必ず自動実行する**（オプトインではない）
- 3エージェントは読み取り専用として動作させる。ファイル編集・コメント投稿は本体（メインスレッド）でのみ行う
